# Valkey 9 coordination/cache source profile (U-DATA-05)

This opt-in overlay defines a future cutover in the **existing**
`agentforge-dev-7801d4a9a4` Compose project. It has not been applied. Existing Redis7
and every current volume remain present and unchanged. Do not start a second local
project, delete the Redis volume, copy its entire keyspace into cache or switch an
application before its new Rust transport seam is integrated and validated.

`docker-compose.valkey.yml` merges last with root Compose, or the current
`deploy/local/compose.yml` + runtime + apps stack, and uses `valkey-split` profile.
All bind paths are relative to the canonical first root Compose file. Pass
`--project-directory` with the repository root if selecting a different first file.
No public Valkey port is published. Separate internal coord/cache networks admit
Gateway, Knowledge API and Knowledge worker; frontend, SDK, Runtime, control and
Python sandbox receive neither these passwords nor network membership. Existing
legacy data-redis membership is retained for rollback, but this overlay removes old
shared-password URLs from the three application environments.

| Instance | Purpose | Policy | Persistence |
| --- | --- | --- | --- |
| coord | Sessions, leases, reservations, rate/quota windows, replay/idempotency |256MiB noeviction | AOF everysec; no truncated AOF acceptance |
| cache | Pure principal/policy/retrieval acceleration |128MiB allkeys-lru | Disposable memory, no AOF/RDB |

Coordination OOM, authentication and transport errors are unavailable/deny outcomes,
never permission to admit, local-memory fallback or cache misses. The Rust client
checks authenticated CLIENT INFO user, Valkey major9, actual maxmemory policy,
nonzero memory bound and healthy AOF writes. `appendfsync everysec` is enforced in
the immutable source config, not inferred from an INFO field that does not expose
that setting. A 70% memory-warning API is available for the metrics/alert integration.
AOF everysec permits recent-state loss after a crash: sessions reauthenticate and
leases expire; PostgreSQL remains the durable authority. Existing usage/queue
adapters retain coord until the separately owned PostgreSQL outbox transition;
this profile does not relabel Valkey streams as durable billing storage.

## Private prerequisites (generated later by the primary)

`deploy/local/valkey.env.example` contains names only. Select and verify the real
`docker.io/valkey/valkey:9.x.y@sha256:<digest>` and its nonroot UID/GID. The example's
9.1.2 tag was checked against the official release/download metadata; no digest or
image existence/architecture/scan result is implied by the placeholder. NativeTools
`valkey_deployment::validate_image` checks explicit major9 digest shape and
`validate_identity` rejects root/placeholders; these are not image admission scans.

The standalone Rust child `valkey_material::generate(repository, new_directory)`
prepares eight independent 256-bit passwords, eight service-only password files and
two hashed ACL files (ten files total), in a new external0700 directory with0600
files. It refuses an existing directory, repository-local material or overwriting
any file, and returns only a count. Its CLI registration belongs to the primary;
no real material was generated by this work. On a partial I/O failure, preserve the
private incomplete directory for controlled inspection; do not silently reuse it.

Prepare server-only coord/cache TLS cert+key files and a public CA bundle. SANs must
cover `valkey-coord` and `valkey-cache` respectively (include separately selected
host-native DNS names if needed). Servers disable plaintext TCP (`port 0`) and
require TLS1.2+ and per-service ACL authentication. `tls-auth-clients no` means this
is verified-server TLS plus ACL passwords, **not** mTLS. Private password files
must be readable by their owning process UID only (0400/0600); configure each
file's actual ownership before the later controlled startup. Valkey daemon TLS key,
ACL and health password inputs belong only to the selected Valkey UID. Gateway and
Knowledge each get only their own two password files. Use regular files/subPath
mounts, not writable/symlink credentials. Never put passwords in URLs/CLI arguments,
reports or shared env files. No full-privilege application/admin password is created.
ACL rotation uses a reviewed replacement file and controlled instance restart;
application users cannot CONFIG/ACL/FLUSH/KEYS arbitrary state.

The Compose health probe authenticates its separate read-only health user over TLS
on **127.0.0.1 inside the same container**. Official valkey-cli9.1.2 `--sni` sends SNI
but does not verify the DNS hostname; it is not the security/readiness proof.
Application readiness must pass the Rust rustls handshake, which keeps hostname
verification enabled and uses the selected CA. No `--insecure` or plaintext fallback
exists. TLS wrong-CA/wrong-DNS and real ACL server tests remain required before cutover.

## Native integration seams

No shared lib/Cargo/bootstrap/Knowledge source was changed here. After the primary
adds `pub mod valkey;` to service-primitives and enables redis1.7.1's documented
`tokio-rustls-comp` feature (never `tls-rustls-insecure`), use:

```rust,ignore
let split = SplitConfig::from_values(&captured_environment, ServiceIdentity::Gateway)?;
if let Some(config) = split {
    let connections = SplitConnections::connect(&config).await?; // coord failure is fatal
    let legacy_redis = Some(connections.coord.coordination_manager());
    // Store typed coord/cache separately; only legacy_redis feeds old coord adapters.
    // CacheAvailability::Unavailable is observable cache bypass, never coord fallback.
}
```

`SplitConfig::from_values` returns None only when **all** new variables are absent;
unknown, partial, wrong-service or insecure settings are fatal. Both explicit
endpoints use rediss, port and /0, no userinfo/query/fragment, different host:port and
different password files. New variables captured once per process are:

- AI_PLATFORM_VALKEY_MODE=split
- AI_PLATFORM_VALKEY_COORD_ENDPOINT / _USERNAME / _PASSWORD_FILE / _CA_FILE
- AI_PLATFORM_VALKEY_CACHE_ENDPOINT / _USERNAME / _PASSWORD_FILE / _CA_FILE

Knowledge startup must call the same API with KnowledgeApi or KnowledgeWorker and
supply coord exclusively to replay/idempotency stores. Never leave a second direct
`redis::Client::open` on the old shared URL in split mode. Opt-in usage consumers must obtain coord.dedicated_manager().await, which creates
a separate TLS/ACL/INFO-verified connection with a five-second response deadline
for existing XREADGROUP BLOCK1000. They must not reuse the admission manager or
EVENT_BUS_REDIS_URL in split mode. Gateway legacy settings
and constructors stay compatible when no split variables are present.

CacheConnection exposes only typed, tenant/service/kind-bound get/set/invalidate;
it does not expose a ConnectionManager. Gateway admits Principal/Policy keys,
Knowledge admits Retrieval keys. Callers must include authorized actor/ACL scope,
resource generation and policy revision in the identity bytes; TTL never replaces
authority/revocation checks. Keys encode a SHA256 tenant hash tag and identity hash.
Cache reads allocate at most1MiB+1 through GETRANGE and reject oversize values before
parsing, writes require a nonempty value and TTL1..300 seconds. Cache reconnection
can call CacheConnection::connect(config.cache()) without touching coord. Existing
bounded process-local retrieval/principal caches are not silently rewritten by this
infrastructure package; their owning business adapters can opt into this cache port.
Existing coordinator key strings remain stable for public-interface compatibility;
Cluster rollout still needs an explicit cross-slot inventory for legacy sessions.

## Verification and remaining acceptance

Observed offline: 16 primitive policy/config/ACL tests and six deployment/material
child tests passed using standalone rustc and cached dependencies. Transport was
not compiled because the shared redis TLS feature/lib registration remains with
the primary. The two real acceptance tests are explicitly ignored until a planned
outage is acknowledged; they were not executed.

Source tests cover TLS endpoint/ACL separation, endpoint and mode mistakes, OOM and
outage denial, AOF/policy mismatch, memory threshold, cache scope/bounds, ACL grants,
private file creation and config/Compose regression negatives. The deployment gate
reads public files only and separately accepts selected public image/UID references.
The child APIs are unregistered until the primary completes shared NativeTools wiring.

No Docker/Cargo/buildx, real Valkey pressure, private credential generation, service
switch, real authentication/TLS, data copy, HA failover or existing-volume mutation
was run. A synthetic digest is only a parser test. Real pressure acceptance must
fill coord to its cap, observe OOM rejection without session/lease eviction, verify
admission remains closed, and separately show cache eviction/bypass cannot affect
coord. Test wrong credentials across all eight users, wrong CA/SAN, lost cache,
lost coord, restart/AOF behavior and the later rollback inside the same project.
