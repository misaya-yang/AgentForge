# 对《AI Assistant 设计宣言》的深度批判性审查

**审查者**: 同一作者，第四轮自我批判
**日期**: 2026-07-16

---

## 总体评价

报告的质量比第一版有质的飞跃——从功能清单变成了设计哲学。但这不意味着它已经足够好。以下是五个结构性问题，每个都指向报告的一个根本缺陷。

---

## 批判 1: "五个信念"仍然是观察，不是设计原则

报告说"失败优先"、"Actor 模式"、"语义压缩"、"全链路流式"、"自我进化"——这些都是 **what**，不是 **how**。

**缺失的东西：决策框架**

一个好的设计原则应该能回答："当我在写代码时，面对 A 和 B 两个选择，这个原则能告诉我选哪个。"

当前的"信念 1：一切都会失败"做不到这一点。它告诉我要"分类错误"，但没有告诉我分类的**维度**是什么。从四个项目中可以提炼出一个真正的决策框架：

```
失败分类的四个维度：

1. 可恢复性 (Recoverability)
   - 瞬态 (Transient): 重试就能解决 (rate_limit, timeout, network_error)
   - 条件可恢复 (Conditional): 需要改变条件 (context_overflow → compact, auth_expired → refresh)
   - 永久 (Permanent): 不应该重试 (content_policy_blocked, billing_expired)

2. 影响范围 (Blast Radius)
   - 单次调用: 只影响当前工具调用 (tool_timeout)
   - 当前轮次: 影响当前 LLM 推理 (context_overflow, thinking_signature_invalid)
   - 会话级: 影响整个会话 (auth_expired, model_not_found)

3. 降级路径 (Degradation Path)
   - 无降级: 必须完全恢复 (auth → refresh token)
   - 功能降级: 可以少做一些事 (image_rejected → text_only mode)
   - 质量降级: 用更差的方式继续 (full_model_down → fallback to smaller model)

4. 用户感知 (User Visibility)
   - 不可见: 自动恢复，用户不需要知道 (retry with backoff)
   - 告知: 恢复成功但需要让用户知道 (switched to fallback model)
   - 阻断: 需要用户做决策后才能继续 (billing required, consent needed)
```

**这**才是一个设计原则。它不只是说"要分类错误"——它给出了分类的维度。

---

## 批判 2: Actor 模式的建议可能解决错问题

报告强烈推荐 Actor 模式，论据是"Agent 运行期间世界不会停止变化"。这个论据是对的，但诊断可能是错的。

**真正的问题不是线性 vs Actor——是 4871 行的函数缺乏边界。**

grok-build 的 Actor 模式是 Rust 类型系统约束下的设计选择。他们**不得不**用 Actor 因为 `!Send` 类型不允许跨线程共享。Python 的 asyncio 没有这个约束——它的单线程协作式模型天然保证了没有真正的并发竞态。

所以对我们的系统来说，真正的问题是：

1. **状态管理混乱**：同一个 `AgentLoop` 实例的字段被不同阶段随意读写，没有明确的所有权
2. **控制流纠缠**：正常流程、错误恢复、取消处理、回退逻辑全混在一个函数里
3. **副作用散落**：持久化、指标上报、事件发射散布在 4871 行中，无法确定何时发生

**这些问题的解不一定是 Actor 模型。**

一个更轻量的方案可能是：

```python
class AgentTurn:
    """单次 turn 的有限状态机 —— 而不是全量 Actor 框架"""
    
    State = Enum('State', [
        'LOADING_CONTEXT',     # 加载记忆/技能/知识库
        'BUILDING_PROMPT',     # 构建系统提示
        'SAMPLING',            # LLM 推理中
        'EXECUTING_TOOLS',     # 工具调用中
        'COMPACTING',          # 上下文压缩中
        'REFLECTING',          # 后台反思中 (非阻塞)
        'COMPLETING',          # 收尾持久化
        'CANCELLED',           # 被取消
        'ERRORED',             # 出错
    ])
    
    # 每个状态有明确的:
    # - 进入条件
    # - 可接收的事件 (cancel, model_switch, health_check)
    # - 退出动作 (持久化、清理、事件发射)
    # - 合法转换目标
```

这比重写整个 loop 为 Actor 框架更务实。它不是 grok-build 的 `tokio::select!`，但它解决了我们实际的问题：**控制流纠缠**。

**所以更准确的建议应该是**：不要抄 Actor 模式，而是做**状态机分解**。Actor 是手段不是目的。

## 批判 3: 压缩策略缺少成本模型

报告说"用 LLM 做语义总结而非字节截断"，但没讨论**代价**。

算一笔账：
- 一次 LLM 摘要调用 (用 gpt-4o-mini): ~500 input tokens + ~200 output tokens ≈ $0.0002
- 一个会话可能触发 3-5 次压缩
- 每天 1000 个会话 = 3000-5000 次压缩调用 = $0.6-1.0/天
- 这是小钱，但加上**延迟**：每次压缩增加 2-5 秒

对于**聊天场景**：用户会感知到 2-5 秒的"卡顿"。简单截断在这里可能**体验更好**——速度快、用户无感知。

对于**编码/长文档场景**：语义保真比延迟重要得多。用户宁可等 5 秒也不要丢失关键上下文。

**所以"三段压缩"的正确设计应该是**：

| 场景 | 主策略 | 触发阈值 | 为什么 |
|------|--------|---------|--------|
| 聊天 | 步内截断 + 步间轻量摘要 | 70% | 延迟敏感，信息衰减快 |
| 编码 | 全量语义压缩 | 85% | 上下文结构重要，等得起 |
| RAG/长文档 | 步间分块压缩 + 尾部保护 | 60% | 检索内容多，需要更早介入 |
| 子代理 | Fork 摘要 (一次性) | 创建时 | 不需要持续压缩 |

报告没有做这个区分。它隐含地假设"语义压缩总是更好"——这不成立。

## 批判 4: 差距分析是具体的，但解决方案是抽象的

报告的"致命问题"部分列出了真实的问题——MCP 无超时、32 个裸 except、全局单例——这些都是从代码中直接读出来的，很好。

但"修复"列太模糊了。"实现 FailoverReason 枚举"——哪些枚举值？针对谁？

这是 Hermes 的 24 个 FailoverReason，按我们实际会触发的频率筛选：

```
我们实际需要的 10 个错误类别 (不是 Hermes 的 24 个):

P0 (每次部署都会遇到):
  CONTEXT_OVERFLOW      → 自动压缩 + 重试
  RATE_LIMITED           → 凭证轮换 + 指数退避
  AUTH_EXPIRED           → 刷新 token + 重试
  TOOL_TIMEOUT           → 断路器 + 降级

P1 (偶尔遇到):
  SERVER_OVERLOADED      → fallback 模型 + 退避
  IMAGE_REJECTED         → text_only 模式降级
  PAYLOAD_TOO_LARGE      → 截断工具结果 + 重试

P2 (特殊场景):
  BILLING_REQUIRED       → 用户通知 + 阻断
  CONTENT_FILTERED       → 告知用户 + 不重试
  MODEL_NOT_AVAILABLE    → fallback 链 + 通知
```

我们不需要 Hermes 的 `llama_cpp_grammar_pattern`（用的不是 llama.cpp）、`oauth_long_context_beta_forbidden`（用的不是 Anthropic OAuth）、`thinking_signature_invalid`（模型还没支持 extended thinking）。

**好的设计不是"实现完整的错误分类系统"——好的设计是"为实际会遇到的错误实现精确的分类"。**

---

## 批判 5: 缺少"不做"的优先级，暗含"全部都要做"

12 周路线图列出了 14 个优化项。但如果只能做 3 个呢？

这是一个有效的约束——团队有日常业务需求，不可能 12 周只做架构改造。

**如果只能做 3 件事，从四个项目的教训来看，优先级应该是**：

| 优先级 | 做什么 | 为什么这是最重要的 |
|--------|--------|-------------------|
| **1** | 错误分类 + 断路器 + MCP 超时 | 这是四个项目的共同底线。每个顶级 agent 都有这些。我们现在是裸奔。 |
| **2** | Prompt 缓存真正生效 | 这是最低成本的性能提升。代码已经写了 90%，就差把缓存信号发给 API。延迟降低 50%+ 成本降低 30%+。 |
| **3** | 流式工具进度 | 这是用户体验的最大短板。用户看着黑盒等 30 秒 vs 看到实时进度——天壤之别。 |

其他 11 项都可以排队。这三项是"不做就不配叫生产系统"的级别。

---

## 总结：报告的核心缺陷与修正

| 缺陷 | 表现 | 修正方向 |
|------|------|---------|
| 观察而非原则 | "五个信念"是 what，不是 how | 每个信念配一个决策框架（如错误分类的四维度） |
| Actor 可能过度 | 推荐 Actor 模式但问题可能是函数分解 | 先做状态机分解，Actor 是手段不是目的 |
| 缺少成本模型 | 语义压缩总是被推荐但没提延迟代价 | 按场景（聊天/编码/RAG）选不同策略 |
| 解决方案抽象 | "实现 FailoverReason"但没说哪些值 | 列出我们实际需要的 10 个类别，不是抄 Hermes 的 24 个 |
| 优先级模糊 | 14 项拉满 12 周但没区分生死线 | 标注如果只能做 3 件事做哪 3 件 |

**最终的最终判断**：这份报告从"功能清单对照表"进步到了"架构哲学宣言"。但它还没有达到**决策工具**的水平——读者看完仍然不知道"明天上班第一行代码写什么"。

一个好的设计文档应该在最后一页回答这个问题：**"明天早上 9 点，我打开 IDE，要做的第一件事是什么？"**

答案是：**打开 agent_loop.py，找到 MCP 工具调用的路径，在 `mcp/manager.py` 第 107 行的闭包外面包一层 `asyncio.wait_for(..., timeout=60)`，然后加一个 `except asyncio.TimeoutError` 返回标准化的 `ToolError(kind=ToolErrorKind.TIMEOUT)`。**

从这个第一行代码开始，逐步生长出完整的错误分类、断路器、超时保护体系。这是所有四个顶级 agent 共同的经验：**可靠性不是设计出来的，是从每个具体的保护措施中长出来的。**
