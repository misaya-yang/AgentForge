# Durable generic task and Batch reconciliation implementation

The default `schema_admitted` task mode selects the durable Gateway admission principal and enables durable tasks only after `require_compatible_schema` succeeds. Failure aborts construction. Explicit `memory` remains available; `durable` remains accepted. No ledger/storage error selects memory.

Batch is separately disabled unless an operator supplies `GATEWAY_PROVIDER_BATCH_PROFILES_JSON`, a JSON array of exact `tenant`, `provider`, `model`, `model_version`, `book_version`, and `api_key` fields. Never publish real credentials in configuration evidence. The initial bounded provider supports the official OpenAI origin and one credential/profile per tenant/provider. A service must also explicitly configure `metadata.provider_batch` with `enabled`, `provider_id`, `model_id`, and `endpoint` matching the task's `parameters.provider_batch`. A separately protected upload-authority grant binds the pre-existing Batch input file to tenant, user, service, model, endpoint and digest; task JSON cannot create a grant. This implementation does not upload files or infer their ownership.

The original [schema proposal](proposals/generic-task-batch-reconciliation.sql) is included in the measured, source-activated [029 successor](canonical-schema-successor-029-source-plan.md). Actual database migration and the accepted-contract marker remain separate activation prerequisites. Missing tables, publication, dedicated Batch rate, or owner-installed accepted contract marker rejects admission before POST. It must be measured and activated by native authority, including grants and canonical fingerprints; do not source it manually. It does not modify frozen 026/027/028 sources.

The configured immutable price publication must contain `Component::Batch`, `Unit::Requests`, USD, and explicit model/book revisions. These terms price **completed Batch requests**; token-priced Batch publications are rejected rather than guessed. The first rate receipt freezes before submission into `price_book_v2_usage_receipts` under `request_type=provider_batch`. A verified terminal provider GET supplies bounded completed/failed/total counts; completed count is quoted using that frozen receipt and recorded idempotently in the same accounting checkpoint table under `batch_receipt_verified`. Existing checkpoint-to-receipt binding remains enforced. The terminal accounting transaction also inserts the original request-meter usage row, applies existing quota/daily/hourly stage consumers, persists their exact observations, and retires both the Batch hold and its dispatch reservation. A stable hold timestamp makes those stage receipts replay-safe. Token facts are NULL/N/A, never fabricated measured zeros. Historic frozen receipts survive a configured price-version change for the same tenant/provider/model.

A committed unique `task_provider_batches` intent is the sole POST permission. Losing an intent COMMIT response, dying before POST, losing a POST response, losing confirmation, or receiving an unknown provider state never resets the claim or sends another POST. The original task remains `claimed_unknown`. Cancellation and terminal reconciliation serialize on the original delivery fence, preserving the first terminal winner.

Fresh same-tenant JWT administrators may inspect `GET /api/v1/tasks/{task_id}/delivery` and invoke `POST /api/v1/tasks/{task_id}/reconcile` with only `claim_id` and optional `provider_job_id`. The job ID is a discovery hint, never terminal evidence. The credential-owning provider adapter performs GET and checks stored nonce/input/endpoint/completion window/job binding; status, result and accounting come from that authenticated observation. Caller-supplied status/result/nonce/retry fields are rejected. Audit, projection and delivery terminal writes commit together. There is no callback replay or operator reset-to-pending API.

## Verification boundaries

Source regression coverage includes explicit schema-gated default selection, rejected forged operator fields, tenant-separated nonreplaceable provider registration, mismatched provider receipt identities/nonces, nonterminal states and invalid accounting counts. Rustfmt parsing and scoped diff whitespace checks ran; Cargo, PostgreSQL, provider and kill-9 tests have **not** run for this source set. Primary owns builds and real-service acceptance. End-to-end Batch acceptance remains open: canonical proposal activation/rollback, credential-backed input grants, explicit published Batch tariffs, real quota/aggregate/capacity/rate and provider conformance, and kill-9 at intent commit / POST / confirmation / reconciliation commit boundaries. Keep the contract marker absent until these activation requirements are accepted.

The Batch lane uses the existing AtomicDispatchAdmission global/tenant GCRA and capacity lease through an internal marker that public request fields cannot construct. This lane does not use the retrying executor. A protected upload grant supplies the request count; an immutable frozen Batch receipt supplies the maximum cost. Under the same per-user advisory lock as ordinary dispatch, a durable hold reserves full request count and ceiling cents. Ordinary dispatch includes these pending Batch holds in its quota snapshot; only an explicitly absent table on old schema selects zero holds. Permission/query failures propagate. The submitting Batch excludes only its exact already-held claim from the second admission snapshot. Unknown holds never expire or release merely because local capacity is released. Terminal evidence must fit the protected count/cost envelope before any usage or counter mutation.

Capacity resolution or lane admission refusal is a distinct `NotDispatched` outcome: the lane has not polled a provider submission future. Only this result releases the persistent quota hold under the shared 71107 per-user lock, with tenant/user/task/request/service/claim/submission-nonce binding and an unconfirmed retained claim. The release immediately gains independent task ownership so caller cancellation while waiting for locks cannot abandon it. A concurrent delivery cancellation that retains the same claim permits this already-authorized release; cancellation alone never authorizes a refund. The hold becomes `released` with its own timestamp; it is never recorded as settled usage. The committed intent remains, so a later observation of the exact released intent returns the same known failure without another POST. The existing delivery finish path projects that failure. Provider errors (including a provider returning `NotDispatched`), cancellation without this prior proof, lease loss, uncertain dispatch marking, and cleanup failure after submission retain Unknown and their quota hold. Released holds cannot subsequently be confirmed or settled. Source regression tests cover these lane and caller-drop boundaries; durable release transactions, proposal triggers, and process kill-9 recovery still require acceptance before activation.
