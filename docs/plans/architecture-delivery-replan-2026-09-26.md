## 2. 为什么会越做越大

| 问题 | 当前证据 | 后续改变 |
| --- | --- | --- |
| 产品“恢复”缺少层次区分 | [AS-03](product-feature-completion-2026-09-23/02-assistant-tools-deliverables.md)同时包含断网、刷新和 Runtime 重启；标注为 P0 验证。历史读取、存活任务重新订阅、进程死亡后的执行续接是不同能力 | 对每种中断明确可恢复对象、持久状态与成功观察；没有实现依据的能力标新增架构工作 |
| 在产品要求上追加内部约束 | 后续提示词要求原 run/turn；[设计](../design/agent-runtime-durable-recovery.md)涉及 Core 恢复入口、工具结果补配、签名 lease 与执行围栏 | 明确产品 run、Core turn、工具 execution/attempt 各自职责。保留当前已授权合同；后续不未经论证就新增跨层身份必须一一相同的条件 |
| 过早横向实现 | 工作树已涉及 Core、App Server、Runtime、Worker、Gateway、迁移与构建链；最关键的同任务重启成功链路尚无验收记录 | 每个完整项目先穿透一个真实代表场景，再扩展支持矩阵。内部阶段由同一会话连续推进，不按文件拆成用户任务 |
| 新增前提在后期才暴露 | epoch 3 来源验证问题在 epoch 4 的隔离数据库测试中暴露，恢复代码已铺开；之前还发生 migrator 镜像落后数据库 | 首先验证该项目必需的迁移/构建前提。遇到前提缺陷，只修导致当前失败的最小合同，单独记录结果 |
| 构建没有固定候选 | 账本明确记录构建期间源码变化导致来源校验拒绝 | 构建使用包含必要未提交文件的只读候选快照；核验该快照。后续源码变更进入下一候选，不降低来源校验 |
| 范围与完成标准不够具体 | DR-01 的 owned_paths 含 `tests/**`、整棵 overlay 等宽泛范围；“统一状态、清理重复适配”缺少替代清单；R1 阶段状态同时保留多个 in_progress | 以运行行为和权威归属限制范围；删除或替代哪一项先列明。一个当前实施包，其他是已验证、待验证或排队 |

审批持久化、旧执行者围栏、回执去重本身不是无关发散；它们是所承诺恢复语义的必要组成。数据库校验修复也有实际失败依据。问题在于依赖验证顺序及变化边界，而不是看到 Python、测试或迁移就认定工作无价值。

## 3. 架构方向

保留现有服务拓扑，本轮不增加执行引擎或开启全平台 Rust 重写。

| 权威归属 | 应负责的事实 | 应避免的重复 |
| --- | --- | --- |
| Codex Core / App Server | 模型与工具循环、Core turn 语义和已支持的恢复原语 | 平台自己实现第二套模型循环；把上游某个恢复函数当成已具备全部平台恢复语义 |
| 平台 Rust Runtime | run 与 Core 的绑定、执行所有权、审批续接、恢复协调及对外事件 | Gateway 或页面自行推断/推进执行终态 |
| Rust Worker | 工具执行身份、dispatch 状态、持久回执和可证明的副作用结果 | Runtime 为既有调用另造一次执行；对未知写动作自动重试 |
| Gateway | 身份、租户授权、模型凭据、配额账本和产品接口 | 自己调度恢复或重放工具；与 Rust 手工维护同一个执行状态机 |
| Web / SDK | 命令提交、事件展示、重新订阅 | 用刷新触发新任务，或把新 run 展示成原任务续接 |
| Knowledge | 知识版本、摄入、检索与资源访问 | 借助手恢复工程顺带重写完整知识服务 |

“统一合同”只在发生真实重复或矛盾的边界上实施：指定一个权威定义，补兼容映射/样例，验证后删除旧实现。它不再作为可以无限追加的独立口号。

## 5. 当前恢复项目怎样继续

保留已经写出的实现，不凭本次复盘重置或重写。建议当前唯一 writer 按下列顺序推进：

1. 完成已复现的 epoch 来源检查修复，证明既有迁移历史保持不可变、新迁移可合法追加，再运行隔离数据库验证。不要借此替换整个迁移框架。
2. 明确本候选可恢复能力与不支持情形；首先在固定候选上证明“一个持久审批跨重启后，原任务完成且工具只执行一次”。若失败，定位到本条调用链，不继续增加其他功能。
3. 正向链路成立后完成既定故障矩阵。以数据库身份/回执、实际工具计数和事件终态共同证明，不能以 Python 测试数量或容器健康代替。
4. 完成候选的独立 review，修复后只重跑受影响验证；源码变化后重新生成对应候选。最终记录实际验收版本、支持边界和回退条件。

第 2 步是内部可行性证据，不是可提前发布的安全认证；取消、授权、未知副作用等必需验证仍是交付门槛。若同 Core turn 恢复经实证需要不可接受的大改，应呈现可复现失败、最小必要改动和产品语义替代方案，由用户决定；不能擅自改成新 run 或只展示历史。

## 6. 后续任务约定

每次给 Sol 一个完整用户能力，同时明确三个信息：可观察结果、允许改变的架构边界、具体完成证据。初始提示词不重复工作目录和仓库规范，不列整套文档必读清单；从一个当前状态入口按需查代码。

不要同时下达“实现能力 + 统一所有合同 + 清理全部历史债 + 全面升级”的组合目标。若发现必要前提，记录它与本项目的直接因果关系；独立改进留到后续。现有文档与执行状态不一致时由实施 owner 一次修正相关入口，不新建平行账本。
