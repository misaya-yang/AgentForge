# 07｜迭代规划、验收与产品决策

## 1. 执行边界

**本轮交付是PRD。** 下列R0～R5是建议的后续迭代，没有启动开发、部署、迁移或付费调用。已有升级程序保持completed_local，不恢复其旧执行指令。

后续启动时，从最新main重新确认事实，为首个明确模块建小范围实现任务；先证明现有功能哪里不满足需求，再修正。已满足且有当前证据的“验证”需求可以直接关闭，不要求重新开发。每批交付都能展示完整用户流程，不把所有模块攒到一个不可审查的大分支。

## 2. 建议迭代顺序

| 迭代 | 用户可得到的结果 | 主要范围 | 依赖与退出标准 |
| --- | --- | --- | --- |
| R0 合同与基线 | 每个模块的真实支持范围和已知问题清楚 | 核对E01～E19，固定角色/状态/能力/任务范围；US-02、TL-04、OB-01、CL-01的基线部分 | 冻结D01/D03/D06/D07及D02现有safe、D04不可豁免硬门；具体冻结时间见决策表。固定测试账号/资料/模型/版本与已有行为，不把本轮PRD检查当基线实测 |
| R1 助手日常任务 | 对话、附件、资料、工具审批、失败/取消与回看可连续使用 | AS-01～AS-10、TL-01～TL-04、AR-01～AR-04；先修AS-02具体问题 | 依赖R0及现有模型/KB；J01～J08及J29正常/失败/恢复通过，保留已有有效能力 |
| R2 知识生命周期 | 资料从上传到引用，再到更新/撤权可维护 | KNO-01～KNO-12、AR-06；EV-01仅先交付待审核样本保存/版本引用切片；需要外部来源时联动TL-05 | 依赖R1引用/状态及R0权限合同，不依赖完整Eval运行/比较；J09～J13、J30通过；重处理失败不丢原有效版本 |
| R3 构建与质量闭环 | 一个Agent从草稿、预览、评测到发布和回滚可用 | AG-01～AG-09、EV-01～EV-08 | 依赖R1/R2；J14～J18通过，发布使用明确版本与有效验证，不扩大首次公开范围 |
| R4 管理与诊断 | 管理员能接模型、管成员/用量、找任务和定位问题 | MO、PG、TK、US、CF、OB的P0/P1；TL-05/06尚未关闭项 | 既有前提缺陷在前面迭代即时修；本迭代完善全管理流程。J19～J26通过，权限与费用口径一致 |
| R5 客户端与整体回归 | 已承诺API/SDK/CLI和Web完成一致场景 | CL-01～CL-06；跨模块回归及所有未关闭P0/P1 | 依赖各相关模块有效合同；J27/J28及所有本轮必需用例通过，未验证目标不冒充支持 |

上述是产品依赖顺序，不是“直到R4才处理鉴权/模型问题”。R1～R3首次使用其他模块的已有能力时，先验证所需的最小切片；P0或阻止该旅程的P1前提未满足，就先修正该切片，不等待后期，也不顺带展开整个管理模块重构。切片通过不表示对应完整需求或模块已经完成。

具体而言：R1的J06仅验证现有授权KB的选择、查询、引用和撤权，不依赖R2全部入库/版本维护功能；KNO-09完整QA矩阵仍在R2。R2的KNO-12/EV-01切片只保存同一权威库的待审核样本，完整评测运行、比较与发布在R3，避免R2/R3循环依赖。

**首个小开发包命名为R1-A：失败消息与历史恢复表达，范围为AS-02。** 它在R0必要基线确认后即可实施并单独验收。R1是覆盖整个助手日常流程的交付里程碑，应拆成多个小包；不得把R1所有需求塞进第一个改动。R1-A通过不代表R1整体通过。

各迭代实施前由开发估算工作量，按缺陷复现和现有可复用程度拆包。本PRD不给没有研发评估依据的日历承诺。R1完成是第一份用户可见交付；所有P0/P1验收关闭后，才可称本次“现有功能完善”完成。TL-07、AR-05、PG-04、TK-04等P2保持独立，可不纳入本轮发布。

## 3. 共用对象与状态定义

| 对象 | 必须表达的用户事实 |
| --- | --- |
| 会话 | 历史归属、当前配置、未发送草稿；会话存在不表示有运行中任务 |
| Run/任务 | 来源、拥有者、已接受/排队/执行中/待审批/成功/失败/取消；unknown按具体执行结果单列 |
| 工具执行 | 动作、目标、关键参数、授权来源、尚未dispatch/已发出/终态；run取消不自动证明外部动作未发生 |
| 文档/索引 | 来源、文档版本、候选处理任务、当前有效索引；候选失败不等于当前版本不可用 |
| Agent版本 | 草稿修订、预览绑定、已发布不可变版本；运行与历史可追溯 |
| 用量 | 实测、估算、未知、待核对；服务成本与客户付款是不同对象 |

前后端可保留既有内部枚举，不要求为此改数据库或统一所有服务的状态机；产品展示映射必须明确定义并有验收。

## 5. 验收环境与指标

### 环境和样本

- Web以当前支持的桌面浏览器和390px窄屏为基线；本地实机沿用内置浏览器。跨浏览器承诺按现有支持表，不临时扩充。
- 至少两个租户、普通成员/租户管理员/平台管理员映射的隔离账号，使用合成资料、合成文件及可验证工具动作。
- 模型使用已配置且可用的默认模型；文本、工具、图片等能力分别挑选真实支持的模型。缺可选provider不阻塞无关功能，但已承诺入口不可因缺测试而记通过。
- 注入可复现的断流、超时、刷新、重启、权限撤销、参数过期和部分失败。受控夹具证明故障规则，真实provider与浏览器证明实际连接链，两者分别记录。
- 开始前固定支持格式/大小/页数、数据量、客户端/语言/架构、模型配置与服务版本。性能验收仍遵守有效产品合同或明确批准的修订，不在测试后降低阈值换通过。

### 产品指标定义

| 指标 | 口径 | 本轮如何使用 |
| --- | --- | --- |
| 核心流程完成率 | 成功完成既定用户结果的场景数 / 实际执行场景数，失败与未运行单列 | P0/P1必需场景全部通过后才能关闭模块；不只计HTTP 200 |
| 异常可恢复率 | 按定义可恢复的失败中，按界面动作完成恢复的数量 / 实际执行可恢复场景数 | 同时记录不可恢复/未知副作用情形，不强行算恢复成功 |
| 状态一致性 | 页面/历史/详情/后端事实不一致的案例数 | 必需用例中不允许已知不一致遗留为PASS |
| 权限与重复执行 | 越权读取/写入、拒绝后dispatch、非幂等重复执行案例数 | 必需负测零违反；任何发现先停止受影响发布 |
| 结果可用性 | 已宣称成功的产物/引用中，能打开且内容正确的数量 | 正文声明不能替代文件/引用核对 |
| 易用性 | 非原实现者能否仅凭页面完成首次流程；卡点与求助次数 | R0记录基线，迭代后对同任务复查；不编造用户满意度或节省时间 |
| 延迟与成本 | 真实首可见响应、最终完成时间、已测/估算/未知用量 | 按任务类型、模型和环境分组，不能混成一个速度分数 |

定义“每个功能完善”时，需要正常与异常流都能完成、已保存结果可恢复、权限边界明确、用户能理解下一步。它不意味着永远无bug或全部SaaS经营能力已经成熟。

## 7. 后续开发交接模板

每个实现任务至少给出：需求ID、用户场景、现有证据、具体问题、保留行为、允许修改范围、API/数据影响、正常与异常验收、回退方式和未验证项。先复用已有能力；需要改公共契约时单独说明，不把PRD表格直接解释成任意架构重构授权。

以AS-02为例：从已保存failed且无正文的合成会话复现 → 比较刷新前后呈现 → 保留已提供的安全错误分类/诊断ID → 让历史消息表达失败和下一步 → 覆盖失败、取消、成功空正文、部分输出四个用例 → 对最终页面与后端终态复核。该任务无需重写Rust内核、重做会话数据库或顺带实现三档权限。

每批完成后记录三类结果：已通过、发现并修复、仍未验证。重要问题修正后由独立reviewer复核相关流程，避免只检查作者新增测试。达到本批退出标准就收口，下一批另行推进。
