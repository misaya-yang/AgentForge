## 0. 给执行 Codex 的硬约束

这是一份需求与架构合同，不是“执行所有历史计划”的指令。先读本页，然后只加载当前工作包需要的分册。初版设计与调查证据已完成；用户随后授权在 `codex/agent-platform-vnext-phase1` 开始一期实现。实现状态以 `deploy/runbooks/agent-platform-vnext/loop-state.json` 为准，验收结果写入对应receipt；本PRD不充当第二份进度账本。

1. **从当前代码增量演进。** Rust Agent 的核心来自已锁定的 codex-harness。本计划关注它与 Gateway、Worker、模型适配器、知识库、SDK、CLI、桌面端的兼容，不重写其模型循环、上下文压缩、规划器或工具选择器。
2. 保留 ADR-006/007/008 的单内核与三个业务边界；保留 ADR-009 的独立本地 CLI。不得把独立 CLI 悄悄改成远程 Gateway 客户端。
3. 一个需求必须连到源码发现、契约、工作包和验收场景。不得以创建文件、通过 mock、编写文档、增加测试数量代替功能完成。
4. `CANDIDATE_80` 是可实际使用的阶段候选；`RELEASE_100` 是该期所有必需验收完成。百分比不是需求覆盖率或完成声明。通过 C80 后继续关闭本期 R100 项，不借下一期需求无限扩大范围。
5. 不以全量 Rust 化、新增微服务、全仓重命名、无收益的抽象、修改测试以适应错误行为作为“专业化”。
6. 当前已有的未提交核心修复文档及其他脏工作必须保留。先判断相关修复是否已在新 HEAD 落地；已修复项只补缺失的直接证据，不重做。
7. 本 PRD 的新增 API、schema、Make gate、目录均明确标为**目标**；实现前必须检查现有合同，存在等价能力时复用。本文不是声称这些目标已经实现。

## 1. 产品定位与问题

“Agent 网管”在本 PRD 中定义为：**管理模型、Agent、知识资产、执行环境与交付质量的统一 Agent Gateway 与工作平台**。它同时支持自托管的多租户平台，以及可独立运行的本地 CLI/桌面工作台。它不扩展成传统网络设备管理系统。

目前项目已有可工作的三域拓扑、单 Rust 内核、混合检索、Agent Studio、Trace/Eval、CLI 启动器和较丰富的门禁。下一期的主要问题是：这些能力的**身份、授权、配置、事件终态、后台任务、制品和质量证据尚未形成同一条可靠链路**。功能入口多，但部分入口的失败语义不同；文档、页面指标与真实行为也存在偏差。

因此，不能把本轮目标写成“再加一个聊天框/RAG/评测页”。目标是让用户完成一个任务时，能知道它用了什么配置、访问了什么资源、为何路由到某模型、哪里失败、能否恢复，以及发布后的质量是否有证据。

### 1.1 对“2026 SOTA”的判定

不存在覆盖网关、RAG、Agent、CLI、桌面端的单一 SOTA 榜单。这里采用截至 2026-09-07 检索到的一手工程资料，评价六个维度：契约与权限一致性、持久执行与恢复、可复现评测、检索与数据生命周期、可观测控制面、可验证分发与客户端体验。资料及其成熟度见 [07：一手资料与决策](07-references-and-decisions.md)。

**结论：方向与现代工程实践一致；当前不能宣称达到专业发布等级，更不能宣称算法效果或性能达到 SOTA。** 已有能力应保留并接通；源码确认的正确性问题、发布证据缺口及新产品需求分开处理。具体依据见 [01：现状与缺口](01-current-state-and-gaps.md)。

### 1.2 主要用户与完整旅程

| 用户 | 要完成的事情 | 完成可见证据 |
| --- | --- | --- |
| 自托管管理员 | 安装、接入模型、配置租户与预算、诊断故障、升级与回滚 | 服务/能力健康、明确失败原因、版本与回滚 receipt |
| Agent 构建者 | 从默认 Assistant 派生 Agent，绑定知识/工具，预览、评测、发布 | 同一不可变版本在预览与发布执行，评测门禁可追溯 |
| 知识管理员 | 上传/同步资料、检查解析、调整检索、发布新索引、撤销权限 | 任务进度、页级来源、检索诊断、可回切索引版本 |
| 最终用户 | Web/CLI/桌面发起任务，批准限定动作，中断后继续，取得文件 | 任务状态一致、结果有来源、没有重复副作用或永久锁死 |
| Eval 维护者 | 定义用例、固定候选、重复试验、解释退化、决定发布 | outcome 与 trace、样本分母、版本指纹和配对比较 |
| 后续 Coding Agent | 定位所有者、修改有限文件、运行真实门禁、恢复长任务 | work package、failure oracle、差异与门禁 receipt 可机器读取 |

## 2. 目标与成功定义

以下是**产品目标/验收目标**，不是当前实测成绩。

| 目标 | 必须得到的结果 | 衡量方式 |
| --- | --- | --- |
| G1 权威一致 | 所有承诺支持的入口使用同一身份、授权、launch、工具身份与终态合同 | 入口 × wire × 租户 × 故障兼容矩阵零未解释差异 |
| G2 任务可靠 | 断流、重启、取消、审批超时、后台 worker 退出均有可恢复或明确不可恢复状态 | 故障注入用例验证 ledger、lease、进程、UI 和副作用 |
| G3 质量可决策 | RAG、Agent 和路由候选可以冻结、回放、比较、阻止回归和回滚 | 实际候选执行、独立 outcome 校验、版本完整性、统计门禁 |
| G4 日常可使用 | 一期平台稳定闭环，二期本地 CLI 与桌面候选有实际生产任务价值 | 每期至少一个跨模块完整旅程，见交付分册 |
| G5 AI 开发可持续 | 需求与源码 owner、命令、测试、证据和生命周期互相可追溯 | 可执行受影响门禁、负向自测、过期例外失败、恢复包 |

专业化判据不采用 LOC 下降、服务数量、支持模型数量、测试数量、宣传标签。采用任务完成率、恢复正确性、数据隔离、真实质量、成本、延迟、安装成功与维护成本。

## 3. 已决定的架构方向

1. **Gateway Control / Agent Execution / Knowledge 三域继续保留。** Eval、路由、治理是逻辑模块，不因命名独立就增加常驻服务。
2. **一套语义，两种部署身份。** Hosted 的凭证、租户与预算归 Gateway；Local 的 provider profile 和本机权限归本地用户及其 App Server。共享版本契约与兼容夹具，不共享秘密和会话归属。
3. **运行 harness、评测 harness、开发 harness 分别有 owner。** 三者通过版本化 run/evidence 合同连接，不放入一个无限扩大的 `core` 包。
4. **权限独立于模型能力。** provider 支持某工具不代表当前任务获准使用它。历史记录、重试、compaction、模型切换都不得扩大授权。
5. **PostgreSQL 是持久执行元数据的事实来源。** Redis 缓存/通知与进程内广播不决定最终正确性；跨 PostgreSQL、Qdrant、对象存储发布以持久状态机和恢复协调保证，而非假设跨库事务。
6. **产品状态必须诚实。** 无样本、尚未探测、采集失败、依赖降级、可用、质量已验证是不同状态。固定数字和未证明认证不得作为运营事实展示。
7. **迁移采用兼容窗口。** 先扩展/回填/双读验证/切读/停止旧写，最后在已声明支持窗口结束后删除。保留旧客户端、运行中任务与 N-1 回滚路径。

详见 [02：目标架构与契约](02-target-architecture-and-contracts.md)。

## 4. 三期交付，三次可独立验证的整体

| 期 | 产品结果 | 必需内容 | 本期不承担 |
| --- | --- | --- | --- |
| 一期：可信运行底座 | 用户能在 Web 使用一个绑定测试 KB 的 Agent 完成任务；管理员能诊断失败；CLI 的已支持平台可独立运行 | 兼容修复、身份/授权、RAG 数据安全、可恢复后台评测、事件恢复、真实状态、运行制品与开发门禁 | 分布式 HA、学习路由、完整桌面发行、全部 RAG 实验算法 |
| 二期：质量驱动工作台 | 从知识入库到 Agent 发布、模型/检索策略比较闭环；CLI 完善；macOS 桌面候选能完成真实任务 | 路由策略与解释、可复现评测、解析后端装配、配置统一、CLI 协议覆盖、桌面 Local/Hosted 双入口 | 公开宣称所有 OS 支持、跨设备透明同步、自动学习后直接放量 |
| 三期：可运营规模与生态 | 经容量证明的多实例服务、受控外部 Agent 接入、跨平台桌面正式分发 | 持久调度所有权/多实例恢复、成本治理、A2A 等边界适配、签名升级与组织策略 | 无收益的服务拆分、绕过发布门禁、无授权远端写操作 |

一期必须包含 KB→Agent→Trace→Eval→诊断的闭环，不能只提交架构目录。二期必须包含对照实验→策略发布→实际任务→退化回滚，不能只增加算法选项。三期必须在故障/升级/旧客户端仍存在时维持任务和数据正确。

具体包、顺序、owned/forbidden paths、停止条件见 [04：分期与工作包](04-delivery-phases-and-work-packages.md)。默认按依赖顺序实现，允许独立只读审查；不得并行写公共集成路径。

## 5. 范围与优先级规则

- `C80_BLOCKER`：本期核心闭环不能启动、权限/租户越界、数据损失、未解释副作用、终态/恢复错误、制品身份未知、无可用回滚。
- `R100_REQUIRED`：本期已经承诺支持的场景、平台、质量与分发仍缺证明。允许先展示候选，但不得省略后直接宣称正式发布。
- `FOLLOW_UP`：属于后一期或实验性增强，有独立进入条件；不能在当前包临时插入。

优先级独立于严重程度：一个 UI 文案问题也可能错误承诺合规；一个没有活栈证明的性能假设不能凭紧急标签阻止所有源码工作。

模块需求以 [03：模块需求](03-module-requirements.md) 的稳定需求 ID 为准。需求不得只在工作包描述中出现而没有验收条款。

### 5.1 明确非目标

- 不重新评价或重造 codex-harness 的内核算法；只更改必要的适配、hook 与合同层。
- 不承诺任意 OpenAI-compatible endpoint 支持所有 hosted tools、多模态、reasoning 或 Responses 行为。
- 不把 MCP、ACP、A2A 混成一个“万能协议”；分别解决工具接入、IDE 客户端、外部 Agent 互操作。
- 不引入未经数据验证的 GraphRAG、全量 agentic RAG、学习路由或向量库更换作为默认。
- 不自动迁移用户密钥、同步本地对话到云端、开放现有 `/internal/v1` 给桌面端。
- 不把扫描不到调用者等同于可删除；不得改写历史 ADR、迁移与证据以消除失败记录。

## 9. 本 PRD 的完成定义

“需求设计完成”不表示升级已实现、全部漏洞已排除、当前 HEAD 已通过活栈验收，或项目达到 SOTA。后续 Codex 从一期 P1-00 开始，刷新事实后按包推进，不从头重复全仓调查。
